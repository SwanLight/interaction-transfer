# 02 — Functional Interaction 表示

表示分为两层：每条示教的完整记录，以及多条示教学出的共享功能要求。两者不能混为一谈。

## 1. 坐标系

- 所有表面点、接触区域和机械作用表达在**被操作物体**坐标系中；
- 物体结果表达为被操作物体相对参照物的变化；
- 不输出 source 的板位姿、速度、动作、数量或身份；
- 同一物体在所有执行器实验中使用同一坐标系和同一表面采样。

### 1.1 "被操作物体"的判定规则

规则：**被操作物体是任务成功判据所作用的那个物体。** 中间传力的工具不是被操作物体。

| 任务 | 被操作物体 | 参照物 | 工具（若有） |
|---|---|---|---|
| 抽屉 | 抽屉 | 柜体 | 无 |
| 旋钮 | 圆盘 | 底座 | 无 |
| 擦拭 | **平面** | 世界/桌面 | 黑板擦（可有可无） |

擦拭的物体系定在平面上，这是 `01` §5.1 两种实现能共享同一份 envelope 的前提：无论中间是否隔着一块黑板擦，"平面上哪片区域被以什么模式、什么压力擦过"是同一件事。工具本身的位姿只进 Oracle Record 的追查字段，不进 envelope。

这条规则也顺带保证了表示对"是否使用工具"不变——这是 idea 的核心主张之一，现在有了可检验的形式。

## 2. 物体表面表示

### 2.1 分辨率

**分辨率由 S4.5 敏感度扫描确定，不预先拍板。** 扫描 {64, 256, 1024, 4096} 四档，取下游成功率饱和点。详见 `05` 实验零。

初值参考（扫描前用于打通管线）：按目标 **pitch ≈ 2 mm** 换算点数，而非固定点数。理由：

- 真实指尖触觉 16×16 覆盖 ~20×20 mm，pitch ≈ 1.25 mm；固定 256 点在 90×45×25 mm 的黑板擦上 pitch ≈ 7.8 mm，会把传感器测到的斑块结构在写进表示时抹平；
- 但物体侧分辨率的真实上限由**三者取最松**：taxel pitch（~1–2 mm）、**面位姿精度**（大概率是真瓶颈）、物体位姿跟踪精度。所以不能只按传感器能力定，必须实测饱和点。

S4.5 的结论同时冻结 `07` 的传感 pitch 指标——这三个数应由同一个实验共同确定，不得各自拍。

### 2.2 每点字段

```text
三维坐标
表面法向
部件标签
interaction weight
contact mode distribution
local traction（如有）
```

Region 用带坐标和法向的点云，不用只有编号的 patch 向量——点云让 executor 知道目标区域在物体上的真实几何位置。

### 2.3 计算代价

PointNet 吃 4096 点 × 2048 并行环境 × 50 Hz 很可能成为训练瓶颈。若 S4.5 判定需要高分辨率：

- 表示按**高分辨率存储**（离线数据集、评估、可视化都用它）；
- executor **输入**用低分辨率全局（FPS 到 256）+ 接触邻域局部高分辨率（ball query 半径 20 mm 内取 256 点）；
- 两者的分辨率分别报告，不要混称。

## 3. 每条示教的 Oracle Interaction Record

未来窗口初值为 1 s、10 个采样点。每个采样点记录以下内容。

### 3.1 Object Effect

- 旋钮：未来关节角增量；
- 抽屉：未来关节位移增量；
- 擦拭：目标区域内 dirt 状态的未来变化。**仅此一项**。

⚠️ **初版还写了"以及擦拭接触体相对平面的未来 6D 位姿增量"，那一条已删除，
理由见 `log/decisions.md` D-42。** 擦拭接触体是黑板擦或执行器自己的接触面——
两者都是 **source 侧的东西**。把它放进 effect，等于让 envelope 携带
"用什么姿态、沿什么路径移动你的手"，那是**动作层面的迁移**，
正是本工作声称不做的事（`plan/00` §1）。而且它会直接违反 §1
"不输出 source 的板位姿、速度、动作"和 §7 第 8 条
"擦拭的 envelope 不得包含工具的存在与否、工具位姿或工具几何"。

擦拭的 effect 只能是**平面自身的表面状态变化**（哪一片 dirt 被清除），
那是物体中心的、与用不用工具无关的。接触体的位姿进 Oracle Record 的
`source/*` 追查字段，不进 envelope。

### 3.2 Interaction Region

把每个接触点分配给最近表面采样点，以法向力加权形成表面热力图。保留空间分布，不只保留质心。

### 3.3 Engage Direction（新增）

每个活跃表面点上，记录**接触体接近/施力的局部方向**（物体系单位向量）。

这个字段单独列出，因为它构成 `05` 的 C2 条件——即 KITE 的几何接触意图（接触位置 + engage 方向）。C1→C2→C3 的增量正是本工作相对 KITE 的差值。见 `00-positioning.md` §2.1。

### 3.4 Contact Mode

每个表面点分别记录：

- no contact；
- sticking；
- sliding；
- separating。

不能只存全局 mode 比例，否则会丢失"哪个区域在滑、哪个区域在支撑"。

### 3.5 Mechanics

同时保留三种候选表示，用实验决定哪种更合适：

1. **Exact 6D wrench**：source 实际产生的合力和合力矩，只作为强信息对照（C5）；
2. **Task-relevant generalized force**：旋钮为绕轴力矩，抽屉为沿导轨力，擦拭为法向压力和切向作用；
3. **Required range**：任务需要的方向和允许幅值范围（C4）。

Exact wrench 不能直接被宣布为最终 functional representation。C4 vs C5 是本工作的最小性结论所在。

### 3.6 Temporal Phase

显式标记：

```text
approach → establish contact → manipulate → release
```

擦拭的 manipulate 阶段进一步标记持续接触与 sliding。

### 3.7 "留出"是对谁留出

E-I 的留出任务（`04` §5.4）**只对执行器留出**。上游的 Shared Structure Model
见过全部三个任务的示教——`plan/README` §2 已明确"不声称任务泛化能力，
泛化的是执行器（下游），不是 interaction model（上游）"。

所以留出的确切含义是：**该执行器的 E-I 在训练中从未收到过该任务的 envelope、
从未见过该任务的物体、其 reward 里从未出现该任务的成功判据**。
envelope 本身由上游产生，这不构成循环论证（`05` §3.3）。

写在这里是因为这一点最容易被读成"上游也没见过"，那是过度声称。

## 4. Shared Functional Envelope

同一任务实例的多条成功示教按任务进度和 phase 对齐后，得到：

- 共同的目标 effect；
- 可接受的 interaction region 集合或概率热图；
- 必须满足的 mode 约束；
- task-relevant mechanics 的方向和稳健范围；
- 允许变化的时长和 phase 边界。

它是**约束集合**，不是所有轨迹的数值平均。

### 4.1 范围如何得到：分位数回归 + conformal 校准

初版把"稳健范围"留作描述性说法，没有可操作定义，于是"必须覆盖成功示教但不过度宽泛"无法判定。落地做法：

**Mechanics 范围**：用 **pinball loss** 直接回归 τ = 0.1 / 0.9 分位数，得到下界和上界。不做"均值 ± k·标准差"——那个假设了对称分布，而接触力的分布通常是单侧截断的。

**Region 允许集合**：模型输出热图后，阈值由 **conformal prediction** 在校准集上标定，使 envelope 具有形式保证：

> 在校准分布下，至少 90% 的成功示教其实际接触区域完全落在 envelope 的允许集合内。

**为什么值得这么做**：这把 `03` §9 那条模糊的通过条件变成两个可测量的数——**coverage**（envelope 覆盖了多少比例的成功示教）与 **width**（envelope 有多宽）。目标函数明确：在 coverage ≥ 90% 的约束下最小化 width。过宽的 envelope 会在 coverage 上通过但在 width 上暴露，无处可藏。

校准集必须独立于训练集和确认集，单独划出。

## 5. 时间同步

source 和 target 不能按绝对墙上时钟硬同步。executor 根据自己的实际进度选择当前窗口：

- 尚未接触时停留在 establish-contact 阶段；
- 接触建立后才进入 manipulate；
- object progress 落后时，desired 窗口不继续盲目前移；
- 允许对 effect 轨迹做有限时间缩放，但不得改变功能目标。

## 6. 表示条件（五档嵌套 + 一档强基线）

报告中使用中文全称，代码可采用括号内简称。

| 条件 | 内容 | 备注 |
|---|---|---|
| **C0** 结果轨迹（Effect） | 只给物体未来变化 | effect-only baseline |
| **C1** +区域（+Region） | 再给允许交互的表面区域 | |
| **C2** +方向（+Direction） | 再给 engage 方向 | **≈ KITE 的几何接触意图** |
| **C3** +模式（+Mode） | 再给接触/滑动约束 | |
| **C4** 完整功能交互（Functional） | 再给 task-relevant mechanics 方向与范围 | **本工作提出的表示** |
| **C5** 精确示教力（Exact-Wrench） | 给 source 精确 6D wrench | 非最小强基线 |

C2 为本版本新增。它是本框架内对 KITE 几何意图的重新实现，论文中表述为 "KITE-style geometric contact intent, reimplemented within our framework"，**不表述为 KITE**——理由见 `00-positioning.md` §2.1。

补充 leave-one-out：从 C4 中分别去掉区域、方向、模式或 mechanics，确认结论不是由固定添加顺序造成。

## 6.1 ⚠️ "不许用 source" 到底禁的是什么（2026-08-30 修订）

`source/` 这个前缀下混着**两类完全不同**的东西，原文没有分开，导致实现时
一度把该用的传感量也禁掉了（D-49 初版因此选了更差的 mode 判据）：

| 类别 | 例子 | 能不能被 oracle 用来算表示 |
|---|---|---|
| 采集侧的**动作与身份** | 指令增量、目标位姿、本体速度、板编号、策略家族 | **绝对不行** |
| 接触面与物体的**测量位姿** | 面的 6D 位姿、被操作物体的位姿 | **可以，而且必须** |

判据是这样一句话：**这个量是"谁在怎么操作"，还是"交互本身的物理性质"？**
接触点的相对滑移由两个刚体的位姿差分得到，那是交互的性质
（Huang 的接触模式分类就按它定义）；而且 `07` §3 的传感方案给的正是
"面相对物体的位姿"——**真实装置测得到的东西，oracle 当然可以用**。

所以禁的是 source **动作与身份**，不是禁传感。第 2 条泄漏检查照此重述。

命名上应当把第二类改叫 `measurement/contact_surface_pose_world`；
本轮为了不重采四份数据集暂时留在 `source/` 下，由
`records.is_measurement()` 显式区分，下次重采时改名（`log/decisions.md` D-52）。

## 7. 泄漏检查

1. 整个场景刚体旋转后，物体系表示逐元素一致；
2. **source 的动作与身份**（指令、目标位姿、本体速度、板编号、策略家族）
   不进入任何模型输出；**接触面与物体的测量位姿不在此列**，见 §6.1；
3. 改变 source 板数量后，表示维度不变；
4. source 策略分类器应能从原始动作识别策略，但不应轻易从 Functional Envelope 识别策略；
5. target executor 看不到 source 身份；
6. 物理参数不直接写入表示，只能通过实际 interaction 体现；
7. 同一 Functional Envelope 不能包含某个执行器专属 joint 或 contact 编号；
8. **擦拭的 envelope 不得包含工具的存在与否、工具位姿或工具几何**——两种实现必须产生可互换的 envelope。检验方式：把实现 (a) 的 envelope 喂给只会实现 (b) 的垫头杆，反之亦然；
9. **region 可推导性检查（新增，重要）**：训练一个只看 `effect + 物体点云` 的探针网络去预测 oracle region。若探针准确率接近直接给 region 的上限，说明该任务上 region 在信息论上是冗余的，**该任务不能用于检验 region 的必要性**，应如实报告而非调参掩盖。

第 9 条是本版本新增。初版的泄漏清单只查"表示里有没有混进 source 信息"，没有查"表示里的字段是否互相可推导"。对刚性单自由度铰接物体，后者是真实存在的问题（见 `01` §3.1）。

### 7.1 第 2 条怎么落地（2026-08-30 定稿，见 D-52 补记与 P-55）

第 2 条不能实现成"把 `source/*` 全删掉再提取一遍"——P-54 之后提取器**必须**读
接触面与物体的测量位姿，那样删完它会直接报错。落地办法是让提取器
（`interaction.SOURCE_READS`）**显式声明它读哪些采集侧字段**，检查围绕这张表做
四件事，**零容差、不设白名单**：

| | 做什么 | 抓什么 |
|---|---|---|
| 2a | 记录里不含任何 `source/*` | 字段泄漏 |
| 2b | 删掉声明表**以外**的全部 `source/*`，重跑提取，逐字段 `array_equal` | 指令/动作影响了输出 |
| 2c | 删掉声明表**以内**的字段，提取器必须**报错** | 在"物体大概在原点"之上静默算出记录（P-54） |
| 2d | 每个 `source/*` 都归成测量或动作之一 | 分类表有缝，新字段无人认领 |

**2b 与 2c 是一对**：单有 2b，"什么都不读"也能通过（那正是 D-49 初版守错规矩的
下场）；单有 2c，读了指令位姿也能通过。

### 7.2 第 9 条实测：`family` 是家族级参照，不是上界

第 9 条原文说的"直接给 region 的上限"，实现里取的是"知道策略家族"。**实测发现
它可以被超过**：旋钮上 probe 0.687 > family 0.553。原因是 `family` 只知道**离散
的家族标签**，而 effect 是**连续量**（接触落在销钉的哪一片随转角连续变化）。
所以这一列应当叫**家族级参照**；`probe > family` 是这条检查最强的阳性信号。

三份实测（P-54 修复后）：**抽屉 0.029 / 擦拭 0.120 / 旋钮 0.687**，
家族级参照 0.151 / 0.127 / 0.553。按本条与 Gate G：**旋钮不能用于检验 region
的必要性**，擦拭要谨慎声称，**抽屉是唯一干净的载体**。见 `05` §2.6。

## 8. 动力学一致性

每帧用接触集合重建物体广义力，并与关节动力学或刚体加速度核对。异常帧、接触缓存溢出和 NaN 必须在进入训练前剔除。
