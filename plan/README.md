# Functional Interaction Transfer：仿真算法验证计划

本目录只规划**仿真中的算法验证**。真实 RGB-D、触觉硬件、surface-pose 硬件和 sim-to-real 暂不进入本轮，但 `07` 记录本轮实验将为硬件指标提供哪些输入。

> **本版本相对初版的核心变更**：主实验从"表示消融"改为"**任务无关执行器的留出任务零样本执行**"。原因见 `log/decisions.md` D-10。初版的表示消融保留为支撑实验。

## 1. 要验证的想法

不同示教者可以用不同动作、接触位置和用力方式完成同一任务。系统不迁移示教者的动作，而是学习一份物体中心的功能交互要求：

- 物体必须产生什么结果；
- 哪些物体表面区域允许参与；
- 接触应处于什么状态；
- 必须产生什么方向或范围的机械作用；
- 交互阶段如何演化。

不同执行器接收同一份功能交互要求，再根据自己的几何和能力产生各自的动作。

本轮需要依次证明四件事：

1. **Shared structure**：明显不同的成功示教能被归纳成同一份功能要求，而不是保留某一个 source 的精确动作。
2. **Information sufficiency**：在相同训练目标下，功能交互比只给物体结果、也比只给几何接触意图，更能支持接触主导任务。
3. **Task-agnostic execution**：执行器学的是"实现任意交互规格"的形态能力，而非某个任务的策略；因此能在**未参与训练的任务**上零样本执行。
4. **Cross-embodiment realization**：多种形态在不改写同一份功能要求的前提下各自实现它。

4. **Sensor sufficiency**（2026-08-30 审计后补入）：**装置能测到的那点东西**
   ——接触面相对物体的位姿 + 面上的触觉——**够不够重建这份交互规格**。

第 3 条是本轮主张，也是相对 KITE 的核心差异（见 `00-positioning.md`）。
第 4 条是 idea 的**硬件前提**，此前被整个推给 Phase II，于是本轮剩下的内容
与 CHORD、接触中心抓取迁移高度重叠；现由 `05` 实验七补上，纯离线。

## 2. 本轮明确不声称什么

见 `00-positioning.md` §4，此处不重复。最容易越界的两条：

- **不声称任务泛化能力。** 泛化的是执行器（下游），不是 interaction model（上游）。上游是 VLA 规模的数据问题，本轮不碰。
- **不声称零样本控制未见形态。** 本轮每个形态各训一个执行器。

## 3. 系统结构

```text
多种双板 source 策略
        ↓
每条示教的 Oracle Interaction Record
        ↓
Shared Structure Model
        ↓
Functional Envelope（约束集合）
        ↓
可行性评价器（形态能力 ∩ 允许集合）
        ↓
交互跟踪执行器 E-I（任务无关）
        ↓
不同动作，相同功能结果
```

## 4. 两个执行器，两个实验，不要混

这是本版本最重要的结构变更。

| | **E-T** 任务奖励执行器 | **E-I** 交互跟踪执行器 |
|---|---|---|
| reward | 任务 reward（角度/开度/清除量） | **交互跟踪 reward，无任务概念** |
| 回答 | 交互信息能否帮助一个学任务的策略 | 该形态能否实现任意交互规格 |
| 主指标 | 成功率、样本效率 | **留出任务零样本成功率** |
| 用途 | 支撑实验（实验一） | **主实验（实验二）**，进入最终系统 |
| 循环论证风险 | 无（`04` §8 禁止交互跟踪 reward） | 无（从未见过留出任务的 reward） |

初版只有 E-T。E-T 单独存在时，"给了 desired region/mode/wrench 就该赢"这件事会被 PPO 自己重新发现所抵消——执行器既能感知当前接触力，又有稠密的物体结果 reward，完全可以自行找到接触点和用力方式。所以 E-T 的对照大概率打平，且打平的原因与 idea 对错无关。E-I 才是 idea 描述的那个东西。

## 5. 任务与执行器

| 任务 | 作用 | 双板 Source | Allegro | 钩杆 | 垫头杆 | 平行夹爪 |
|---|---|:---:|:---:|:---:|:---:|:---:|
| 抽屉 | 阴性对照 + 管线打通 | ✓ | ✓ | ✓ | 物理不可行 | ✓ |
| 旋钮 | region 与 task-relevant torque | ✓ | ✓ | ✓ | 物理不可行 | 几何自检定 |
| **擦拭** | **主任务**；持续接触、压力、sliding | ✓ | ✓ | 物理不可行 | ✓ | ✓ |

**推进顺序：抽屉 → 擦拭 → 旋钮。** 抽屉只用于打通管线（它是预期阴性对照，不要在上面做第一个表示实验）；擦拭是最可能产生正结果的任务，管线一通立刻上；旋钮作支撑。

**擦拭任务已重新定义为"清除目标区域的污渍"，允许两种实现**：(a) 抓工具擦，(b) 用自身接触面直擦。两者产生同一份 envelope（物体系 = 平面）。这使擦拭从 1 个主执行器扩到 3 个，并且四宫格里"有的抓工具、有的直接用手掌"是最有说服力的一格。见 `log/decisions.md` D-12。

不要求每个执行器完成每个任务。不可行组合应被识别，而不是强行修改物体迁就执行器。

## 6. 五个信息条件（嵌套）

```text
C0 结果轨迹        Effect
C1 +区域           +Region
C2 +engage 方向    ≈ KITE 的几何接触意图
C3 +接触模式       +Mode
C4 +力的方向与范围  ← 本工作提出的表示
C5 精确示教 6D 力   非最小强基线
```

C2 是新增的。它是本框架内对 KITE 的重新实现，不是复刻 KITE 系统。加上它之后，序列一眼能看出本工作相对 KITE 多了什么、多的那部分值不值。

## 7. 步骤和硬闸门

| 步骤 | 内容 | 通过条件 |
|---|---|---|
| S0 | 固定版本、可视化与录像 | 能稳定生成视频和评估报告 |
| S1 | 资产、碰撞和几何可行性 | 每个可行 task×executor 组合通过脚本自检 |
| S2 | 脚本可行性（强制）+ Expert（按需） | A1 脚本能完成；A2 Expert 能明确学会（不要求 95%），见 D-30/D-32 |
| S3 | 多策略 Source 数据 | 每个任务至少3种明确策略，均稳定成功 |
| S4 | Oracle Interaction Record | 坐标、动力学一致性和泄漏检查全部通过 |
| S4.5 | **分辨率敏感度扫描** | 确定表面点数，同时冻结 `07` 的传感 pitch 指标 |
| **S4.6** | **传感可观测性**（`05` §0.1，2026-08-30 审计后新增） | 装置能测的子集能重建出交互规格；冻结 `07` §1 的面位姿精度与触觉模态 |
| S5 | Shared Structure Model | 未见 source 策略上仍能输出正确 functional envelope |
| S6 | **E-I 交互跟踪执行器** | 训练任务上跟踪成功率≥80%，可行性评价器 AUC≥0.85 |
| S7 | **E-I 留出任务零样本** | **主闸门**，见 `05` Gate E |
| S8 | E-T 信息条件对照 | 相同奖励下比较 C0–C5，得到可重复结论 |
| S9 | 扰动恢复与鲁棒性 | 见 `05` 实验四 |
| S10 | Cross-embodiment 与反事实实验 | 同一未改写 envelope 被至少三种形态实现 |

不得因为某个 baseline 表现太好而不断修改任务，直到它失败。场景参数只允许在开发集上调整；确认集冻结后不再改。

## 8. 三类模型，不要混淆

| 模型 | 作用 | 是否进入最终系统 |
|---|---|:---:|
| Privileged Expert | 检查环境、控制和 reward 是否可学，提供性能上限 | 否 |
| Shared Structure Model | 从不同 source 示教中提取共享功能结构 | 是 |
| E-I 交互跟踪执行器 + 可行性评价器 | 根据功能结构产生某一执行器自己的动作 | 是 |
| E-T 任务奖励执行器 | 信息条件对照实验的载体 | 否 |

任何阶段失败都先回到其上一个闸门，不同时修改场景、表示和训练算法。
