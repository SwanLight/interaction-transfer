## P-01 · 接触传感器全是零

**现象**：`ContactSensor` 读出来的力全是 0，明明物体在接触。

**原因**：PhysX 的 ContactReporter 没激活。

**解法**：在**资产的 spawner**（不是 sensor cfg）上加 `activate_contact_sensors=True`。

## P-02 · 判不出 stick / slide ⚠️ 解法已失效，见 P-16

**现象**：切向力永远是 0，无法区分粘滞和滑动。

**原因**：`net_forces_w` **只是法向接触力之和**，不含切向分量。实测确认：静止时 `net_forces_w = [0, 0, 4.9050]`，切向分量恒为 0。

**旧解法（在 0.48.0 上无效）**：~~`ContactSensorCfg(track_friction_forces=True)`~~ —— **该配置项不存在**。

**现行解法**：见 **P-16**。

## P-03 · 接触点静默丢失

**现象**：接触点数量明显偏少，一致性校验（`plan/02` §7）残差异常大。

**原因**：`max_contact_data_count_per_prim` 默认只有 **4**，contact-rich 场景必然溢出，而且**不报错**。

**解法**：调到 64。这是首选排查项——一致性校验标记率高时先查这个。

## P-04 · contact_pos_w 出现 NaN ⚠️ 归因已修正（2026-08-27 实测）

**现象**：数据链里冒出 NaN，训练直接崩。

**~~旧归因~~**：~~reset 后被填成 `torch.nan`~~ —— 不准确。

**真实原因**：**NaN 是"该碰撞对当前未接触"的哨兵值，是设计如此，不是 bug。** 本地源码 docstring 原文：

```python
contact_pos_w: torch.Tensor | None = None
"""Average of the positions of contact points between sensor body and filter prim in world frame.
   Shape is (N, B, M, 3) ...
   Collision pairs not in contact will result in NaN.
"""
```

任何时刻只要该 (sensor, filter) 对没有接触，就是 NaN，与 reset 无关。

**解法**：

1. **把 NaN 当信息用**：`torch.isnan(contact_pos_w)` 直接就是 `no-contact` 判据，正好对应 `plan/02` §3.4 的第一档，不需要另外设力阈值；
2. 进入任何数值运算前 `torch.nan_to_num()` 或掩码，否则会顺着策略梯度传播；
3. **若观察到"明明在接触却全是 NaN"，先查 P-17**——多半是 filter 目标不是刚体，压根没配上对。

## P-05 · force_matrix_w 返回 None

**现象**：想拿"某个 body 对某个物体"的成对力，拿到 `None`。

**原因**：Isaac Lab 目前只支持 **many-to-one** 的接触力过滤；覆盖多个 body 的 sensor 上直接返回 `None`。

**解法**：要么拆成多个单 body sensor，要么改用 `ContactSensor.contact_physx_view.get_contact_data()` 取原始数据自己配对。

## P-06 · headless 下没有画面/录不出视频

**现象**：加了 `--video` 但没有 mp4，或者报渲染错误。

**原因**：headless 默认加载 `isaaclab.python.headless.kit`，没有渲染能力。

**解法**：必须同时加 `--enable_cameras`，它才会切到 `isaaclab.python.headless.rendering.kit`。另外确认 `ffmpeg` 已安装。

## P-09 · 采集板的接触力没有物理意义

**现象**：板能施加任意大的力，Mechanics 字段数值离谱。

**原因**：把板设成了 kinematic body。kinematic body 不参与动力学求解，能施加无限大的力。

**解法**：板必须是**普通刚体 + PD 外力驱动**（`plan/01` §4.1）。自检判据：自由落体后稳态接触力 ≈ mg。

## P-11 · Region 其实是从 effect 推出来的

**现象**：C1（+区域）相比 C0 毫无提升，或者提升不稳定。

**原因**：对刚性单自由度铰接物体，`effect + 物体几何` 在构造上几乎蕴含 region——销钉在点云里直接可见，转轴由 effect 推出。执行器不需要任何人告诉它去哪接触。这不是"捷径没堵死"，是这类物理系统本身如此。

**解法**：

1. 跑 `plan/02` §7 第 9 条的**可推导性探针**（只看 effect + 点云预测 region）先确认；
2. 若确认冗余，要么让"几何可达但功能后果不同"的区域存在（旋钮的轮缘低摩擦，D-14），要么如实报告该任务不适合检验 region；
3. **不要靠调随机化范围来制造差距**——那是调到 baseline 失败为止。

---

## P-12 · E-I 的 reward 里混进了任务

**现象**：E-I 在留出任务上零样本成功率意外地高，或者训练时收敛得意外地快。

**原因**：任务信息从后门进来了。常见途径：

- reward 里保留了 success bonus 或 dirt 清除量；
- effect 目标从环境配置读取而非从指令通道读取；
- 环境 reset 逻辑按任务分支，执行器能从初始状态分布反推任务；
- curriculum 里为了调试临时加了任务项，忘了删。

**解法**：`plan/04` §5.1 有明令禁止清单。在 dataloader 和 reward 函数里都加**断言**，并把断言日志存档——`plan/06` §7 要求每次 eval 前查这个日志。不靠自觉。

## P-13 · 留出任务差的时候，把它加进训练

**现象**：数字突然好看了。

**原因**：这是本项目最容易破防的地方。留出任务差 → 加数据 → 立刻好看 → 主张归零，且很难被自己发现。

**解法**：留出任务差时的**唯一**允许动作是扩预训练物体集（`plan/03` §2.4）。扩两轮仍不成立，如实报告 Gate E 未通过。写进 `decisions.md`，不要静默处理。

## P-14 · Envelope 靠"变宽"通过验收

**现象**：coverage 轻松达到 95%+，下游成功率也不错。

**原因**：envelope 宽到几乎不约束任何东西。只报 coverage 时这完全看不出来。

**解法**：**coverage 和 width 必须同时报**（`plan/03` §8.1、`plan/06` §2.3）。目标是 coverage ≥90% 约束下最小化 width。另外 mechanics 范围不要用"均值 ± k·标准差"——接触力分布通常单侧截断，对称假设不成立，用 pinball loss 回归分位数。

## P-15 · 四宫格四格用了不同的 envelope

**现象**：跨形态视频看起来很漂亮。

**原因**：为了让每一格都成功，各自用了各自 target 上表现最好的那条 envelope，或者对 envelope 做了 target-specific 的微调。这样整张图的意义就没了。

**解法**：四格必须来自**同一个 envelope 文件**，在视频里标出该文件的 hash（`plan/06` §3.1、§7）。允许 target 在 envelope 的允许集合内选择具体实现（那正是可行性评价器做的事），但**不允许把值改到允许集合之外**——后者属于 embodiment-specific adaptation，必须单独成节报告（`plan/05` §4.2）。

## P-16 · 拿不到摩擦力（stick/slide 判不出）

**现象**：`ContactSensorCfg` 里没有 `track_friction_forces`，`ContactSensorData` 里没有任何摩擦力字段。

**原因**：**版本过旧。** 该功能由 [PR #3563](https://github.com/isaac-sim/IsaacLab/pull/3563) 引入，**2025-12-10** 合并进 main。本地 isaaclab 版本 0.48.0，changelog 日期 **2025-11-10**，早一个月。不是被移除，是还没加进来。

**解法**：绕过 Isaac Lab 包装层，直接调底层 PhysX tensor view：

```python
# 前提：ContactSensorCfg 必须设 filter_prim_paths_expr（非空）
#       且 max_contact_data_count_per_prim >= 1
ff, fpts, counts, start = sensor.contact_physx_view.get_friction_data(dt=sim_physics_dt)
```

**实测验证**（`/tmp/verify3.py`，mass=0.5 kg，μ=0.4，μmg=1.962 N）：

| 施加力 | 摩擦力(单 env) | 速度 | 模式 |
|---:|---:|---:|---|
| 1.0 N | 1.000 N | ~0 | STICK（静摩擦跟随外力） |
| 1.5 N | 1.500 N | ~0 | STICK |
| 2.5 N | **1.962 N** | 0.54 m/s | SLIDE（饱和到 μN） |
| 3.0 N | **1.962 N** | 1.04 m/s | SLIDE |

教科书级库仑摩擦。**stick/slide 判据**：`|Ff| < μN` → stick；`|Ff| ≈ μN 且 v_tangential > 0` → slide。

**为什么不升级**：upstream 的 `friction_forces_w` 形状是 `(N,B,M,3)`，是**按 filter body 聚合求和**的，把空间分布抹掉了；而 `plan/02` §3.2 要的是逐接触点的力+位置+法向。升级之后仍然要调这两个底层接口。见 `decisions.md` D-20。

## P-17 · filter 相关的数据全是零 / 全是 NaN ⚠️ 最容易误判成 Isaac Lab bug

**现象**：物体明明压在地板上，`net_forces_w` 也正确（= mg），但是：

- `force_matrix_w = [0, 0, 0]`
- `contact_pos_w` 100% NaN
- `get_friction_data()` 全零
- `get_contact_data()` 的 **`counts = [0, 0]`**

**原因**：**filter 目标不是 rigid body。** PhysX 的成对接触过滤要求**两侧都是刚体**；只有 `collision_props` 而无 `rigid_props` 的静态碰撞体不会注册成可过滤的接触对。

`net_forces_w` 仍然正确，因为它**不走 filter 通道**——这个不一致极具迷惑性，会让人以为是传感器 bug。

**解法**：所有 filter 目标建成刚体。不动的东西（地板、桌面、柜体）用：

```python
rigid_props=sim_utils.RigidBodyPropertiesCfg(kinematic_enabled=True)
```

**首选排查项**：拿不到 filter 数据时，第一个看 `get_contact_data(dt)[4]`（counts）。是 0 就是没配上对，不用再往下查。

**对本项目的影响**：`plan/01` §1 已加硬规则 7。擦拭平面、抽屉柜体如果建成静态碰撞体，**接触区域和摩擦力全部拿不到**，`plan/02` 的 Interaction Region 和 Contact Mode 两个字段直接作废。

## P-18 · 逐点接触数据是按 env 打包的，直接求和会串环境

**现象**：摩擦力/接触力数值恰好是预期的 N 倍（N = env 数）。

**原因**：`get_contact_data()` / `get_friction_data()` 返回的是**扁平打包 buffer**，形状 `(max_contact_data_count, 3)`，其中 `max_contact_data_count = max_contact_data_count_per_prim × num_envs × num_sensor_bodies`。所有 env 的接触点挤在同一个数组里。

实测：2 env × 每 env 4 个接触点 → 8 行非零，`counts = [4, 4]`，`start_idx = [0, 4]`。直接 `.sum(dim=0)` 会把两个 env 加在一起，正好差 2 倍。

**解法**：用 `counts` 和 `start_idx` 切片：

```python
forces, points, normals, seps, counts, start = view.get_contact_data(dt=dt)
for e in range(num_envs):
    s, n = start[e, 0].item(), counts[e, 0].item()
    env_points  = points[s:s+n]      # 该 env 的接触点
    env_forces  = forces[s:s+n]
    env_normals = normals[s:s+n]
```

**这层切片逻辑应该封装成项目自己的工具函数**（约 30 行），产出 `plan/02` §3.2 需要的"逐接触点 位置 / 法向 / 法向力 / 摩擦力"，不要在每个环境里重复写。

## P-19 · headless 下 `sim.step()` 卡死、`app.close()` 挂起

**日期**：2026-08-27（S1 开发时踩到）

**现象**：脚本跑到第一次物理步进就停住。进程还在，但 **CPU 0%、日志不增长、GPU 显存已分配但利用率 0%**。等 15 分钟也不动。

**原因**：两个独立问题，都出在渲染路径上。

1. `SimulationContext.step()` 默认 `render=True`。headless 且未加 `--enable_cameras` 时没有渲染能力，调用会阻塞。这和 P-06/P-07 是同一类问题，只是发生在 API 层而不是命令行层。
2. `SimulationApp.close()` 在本环境同样会挂起。最小复现脚本十步全部跑完、打印完最后一行，仍然 `timeout 124`——卡在关闭阶段。

**解法**：

```python
sim.step(render=False)      # 所有不需要出图的地方一律关渲染

...
# 报告落盘后直接退出，不走优雅关闭
sys.stdout.flush()
os._exit(exit_code)
```

`os._exit()` 跳过 atexit 和析构，对自检/评估脚本没有副作用（结果已经写文件了）。真正需要录像的评估脚本另说，那时必须加 `--enable_cameras`（P-06）。

**排查提示**：区分"卡死"和"慢"看 CPU——慢是 100%，卡死是 0%。本项目里 0% CPU + 显存已占，基本就是渲染阻塞。

## P-20 · `pkill -f <pattern>` 会杀掉自己所在的 shell

**日期**：2026-08-27（连踩两次）

**现象**：`ssh host 'pkill -f foo.py; cat > /tmp/foo.py'` 之后文件没被写入；或者 `pgrep -f foo.py` 明明进程已结束却一直报"运行中"。

**原因**：`pkill -f` / `pgrep -f` 匹配**完整命令行**，而执行它的那个 `bash -c` 的命令行里就含有这个模式字符串，于是匹配到自己。`pkill` 把自己所在的 shell 杀掉，后续命令全部不执行；`pgrep` 则永远至少匹配到 1 个。

**解法**：

```bash
pgrep -f "[f]oo.py"     # 字符类：模式本身不含字面 "foo.py"
```

或者把 kill 和后续操作拆成两条独立的 ssh 调用。

**代价**：这个坑最恶心的地方是**它静默失败**——第二次踩到时，我以为是资产生成有问题，实际上是生成脚本压根没被写进去。看到"命令明明跑了但文件没变"，先怀疑这个。

## P-21 · `set_joint_effort_target` 会一直保持，不会自动清零 ⚠️ 最难查的一个

**日期**：2026-08-28（S1，查了两小时）

**现象**：前一段测试里给关节施加过力矩，之后的测试中物体的**几何位置全错**——按配置算出的目标位姿完全对不上，执行器"穿过"物体却读不到任何接触。

**原因**：Isaac Lab 的 `set_joint_effort_target()` 设的是**持续指令**，不调用就一直保持上次的值。S1 里旋钮的"已知力矩响应"测试施加 1.5 N·m 把圆盘推到限位 3.491 rad（=200°），之后的摩擦标定阶段圆盘**仍在被 1.5 N·m 驱动**，销钉早就不在角度 0，而标定的目标位姿是按角度 0 算的。

**为什么极难定位**：

- 轮缘那一半**照常工作**（圆盘轴对称，转到哪都一样），只有销钉那一半失败——看起来像"销钉碰撞体有问题"；
- 单独测销钉碰撞体（扔球）**完全正常**；
- `write_joint_state_to_sim(0, 0)` 复位后下一步就又被推回去了，看不出来。

**解法**：换阶段时**显式清零**，并在新阶段的每一步持续清零：

```python
zero = torch.zeros(num_envs, num_joints, device=device)
knob.set_joint_effort_target(zero)
knob.write_joint_state_to_sim(zero, zero)
# 新阶段的每一步也要
def step_fn(i):
    knob.set_joint_effort_target(zero)
    ...
```

**排查提示**：几何对不上时，先打印物体**当前实际关节角**，不要相信"我 reset 过了"。

## P-22 · 接触力峰值包含撞击瞬态，不能当"稳态能传多少力"用

**日期**：2026-08-28

**现象**：明明指令法向力 25 N，实测峰值 66.5 N。

**原因**：物体接触瞬间的冲击尖峰。用峰值去论证"在安全力上限内能传多少力矩"，前提直接不成立——因为力早就超了上限。

**解法**：统计时过滤掉超出指令值的样本：

```python
if fnv > MAX_NORMAL_FORCE * 1.15:
```

## P-25 · 可视化脚本的动作设计错了，会让正确的结论看起来是错的

**日期**：2026-08-28（S0）

**现象**：S1 数字全对，但录出来的视频要么看不出在验证什么，要么给出相反印象。

**三个实例**：

1. **推子飞出画面**：轮缘那段数字正确（圆盘没转），但画面里推子飞走了，观众合理地理解成"推子飞了所以没转"，而不是"摩擦不够所以没转"。
2. **两种情况用了同一条轨迹**：把销钉也写成"径向压紧 + 沿圆周走"——力穿过转轴，力矩恒为零，Δθ=0.0000。**视频看起来像销钉也推不动，与 D-14 的结论完全相反。**
3. **让推子追着销钉走**：推子的位置目标随圆盘一起动，两者互相拉扯，只转到 +0.13 rad（直线推法能到 +1.52）。

**解法**：可视化的动作必须**忠实反映被验证的物理**，不能图省事统一。旋钮的两种情况本来就不同：

```
销钉：切向直推      τ = F·r        与 μ 无关
轮缘：径向压+切向拖  τ = μ·F·R      只能靠摩擦
```

**教训**：视频不是"把数字配个画面"，它是独立的一道检查。`plan/06` §7 要求人工看视频，正是因为它能抓到数字抓不到的东西——但前提是**视频本身得是对的**。

## P-26 · 开环推动的最终转角对推力**非单调**，不能当稳健指标

**日期**：2026-08-28（S0 复核用户质疑时发现）

**现象**：用直线推法推销钉，改变法向力：

| 法向力 | 最终 Δθ |
|---:|---:|
| 10 N | +0.234 rad |
| 15 N | +0.392 rad |
| 20 N | **+0.217 rad** ← 比 15 N 还少 |
| 25 N | +1.516 rad |

**原因**：结果不由"力够不够"决定，而由**接触维持多久**决定。开环直线推时，推子沿固定方向被力控加速；圆盘一转，销钉沿切向离开推子的位置窗口，接触断开。**力越大推子加速越快、越早脱离**，传递的总冲量反而可能更小。这是接触断裂时机主导的准混沌过程，对参数敏感。

**这不影响 S1 的结论**：D-14 的判据是**接触期间传递到轴的力矩**（τ_rim=0.170 / τ_need=0.420 / τ_pin=23.5），不是最终转角。力矩在接触瞬间测量，与接触持续多久无关。转角只在 S0 录像里作示意。

**这也不是任务设计的问题**：RL 训练出的策略是闭环的，会主动维持接触；只有我这段开环脚本才会脱开。但**不能拿开环转角当任何结论的依据**。

**教训**：报告里引用任何数字之前，先问"它对参数敏感吗"。扫一下就知道了，成本很低。用户的一句质疑（"是不是阻力太大"）直接暴露了这个问题——**质疑值得认真扫一遍，而不是拿解析式糊过去**。我最初的解析估算（τ_need/r = 8.1 N）就是错的，实测 10 N 远远不够。

## P-27 · 接触力尖峰 4384 N 把奖励曲线炸掉，而平均值只有 13 N ⭐

**日期**：2026-08-28（S2 训练调试）

**现象**：PPO 训练 239 轮曲线全程不收敛，在 **+55 和 −256 之间来回甩**，
从头到尾没稳过。评估显示 checkpoint 100 成功率 36.4%，checkpoint 200 反而 **0%**。

**排查过程（三次猜测全错，第四次靠测量）**：

我先后猜了「奖励量纲失衡」「提前终止刷分」「sign() 造成悬崖」——
都改了，都没解决。因为**我只有总 reward，看不见是哪一项在爆**。

加上分项记录之后一次就定位了：

```
diag/contact_force_max_N:  4383.6   ← 峰值
diag/contact_force_N:        12.9   ← 均值
```

**原因（两层）**：

1. **表层**：力惩罚 `w_force × (力 − 上限)` 是**无界**的。4384 N 的尖峰
   单步就扣掉 (4384−25)×0.05 ≈ 218 分。曲线的 −256 就是这么来的。
2. **根因**：`max_depenetration_velocity=5.0` 允许求解器用 5 m/s 的速度把
   互相穿透的物体推开，冲量巨大。**这才是 4384 N 的来源**，不是控制器给的力
   （PD 的 max_force 只有 180 N）。

**解法（两层都要修，只修表层等于掩盖）**：

```python
# 表层：惩罚封顶
over = (force - max_force).clamp(min=0.0, max=20.0)

# 根因：限制穿透恢复速度
sim_utils.RigidBodyPropertiesCfg(
    max_depenetration_velocity=1.0,   # 默认 5.0
    linear_damping=0.05, angular_damping=0.05,
)
```

**效果**：

| | 峰值接触力 | reward 曲线 |
|---|---:|---|
| 修复前 | 4383.6 N | `15, -256, -190, -52, 4, 33 … -160, -91, 17` 全程乱甩 |
| 只封顶 | 4383.6 N | `58, 31, 14, -7 … 54, 55, 50, 49, 47, 45, 47` 稳在 +45~55 |
| 两层都修 | **17.3 / 5.1 N** | 落进 25 N 安全上限内 |

**教训（这条最重要）**：

**奖励分项记录应该在写 reward 的时候就加上，不是等训练不收敛了再补。**
我在前面几轮一直强调「别猜，去测」，结果自己在奖励调试上猜了三轮。
成本是 239 轮作废的训练 + 三次无效修改。

所有新任务环境的 `_get_rewards` 都必须写进 `extras["log"]`：
每一项的均值 + 关键诊断量（接触力峰值、物体状态）。

## P-28 · 成功率 100% 的策略在「捅一下让物体自己滑」 ⭐

**日期**：2026-08-28（用户看录像时质疑，实测证实）

**现象**：抽屉×钩杆 Expert 固定/随机环境均 **100%** 成功，画面上抽屉确实被拉开了。
但用户看录像后说：「棍子是往抽屉靠的而不是往外拉，就像棍子靠墙慢慢滑下来，
而墙却反常地跟着棍子方向被拉走」。

**实测（逐控制步记录开度/速度/接触力）**：

| 步 | 速度 mm/s | 接触力 N | 接触点 |
|---:|---:|---:|---:|
| 18–30 | +196 → +214 | 6–13 | 1 |
| **36–48** | **+185 → +48** | **0** | **0** |
| **108–132** | **+238 → +70** | **全 0** | **全 0** |

**抽屉打开的过程中，60% 的控制步接触力为零。** 无接触段的速度衰减
（238 → 70 mm/s 用 0.48 s）反解出阻尼 **3.06**，正是配置的 `damping=3.0`
——确认是**自由滑行**。

**根因**：滑行距离 = v·m/c = 0.2 × 1.2 / 3.0 = **80 mm**，而抽屉总行程才 180 mm。
**一次冲量能滑完大半**，策略根本不需要持续施力。

**修复**：阻尼 3.0 → **30.0**，滑行距离降到 8 mm。

**修复后暴露的第二个问题**：阻尼提高后脚本验证从 180 mm 掉到 **3.6 mm**，
钩杆飞到 319 mm 外。因为原设计让横钩指 +Y 纯避让，拉力全靠
**主杆圆柱压把手圆柱**——两根轴垂直的圆柱是**点接触**，力一大就滑脱。

**第二次修复**：改成三段式**真正勾住**——下探时横钩转 +Y 避让，到位后绕 Z
转 90° 让横钩伸到把手杆**下方**，再拉。主杆压把手背面提供拉力，
横钩挡住向上脱出 → **形封闭**。结果 100% 达标，接触力 13–27 N。

**两条教训**：

1. **成功率不能替代人工看画面。** 100% 的策略在做一件不是操作的事。
   数字、甚至「无穿模无瞬移」都看不出来——是用户盯着录像发现的。
2. **物理参数会决定策略学到什么。** 阻尼太小，「捅一下」就是最优解，
   任何 reward 设计都挡不住。**要让策略学会持续接触，得让环境物理上
   要求持续接触**，而不是去写「必须一直接触」的奖励项。

## P-29 · 不 pin GPU 时，第一次施加外力就 CUDA illegal memory access ⭐

**日期**：2026-08-28（S3 起步，卡了整整一轮）

**现象**：任何往浮动刚体上施加外力的脚本，在第一次
`scene.write_data_to_sim()` 真正提交非零力时直接崩：

```
[Error] [omni.physx.tensors.plugin] CUDA error: an illegal memory access was
        encountered: .../gpu/GpuRigidBodyView.cpp: 810
RuntimeError: copy_if failed on 2nd step: cudaErrorIllegalAddress
```

有时报在 `CudaKernels.cu:1498` / `Failed to submit rigid body forces`，
是同一个东西的不同暴露点。

**原因**：**服务器有 8 张卡，启动时没有 pin `CUDA_VISIBLE_DEVICES`。**
Isaac Sim 启动日志里 8 张卡全是 `Active: Yes`，PhysX 的 GPU 管线和
tensor API 的缓冲不在同一个设备上，提交外力时越界。

**注意 `SimulationCfg(device="cuda:0")` 挡不住**——那只设 Isaac Lab 侧的
torch 设备，不改 PhysX 选卡。

**解法**：所有 Isaac 脚本一律 pin 单卡：

```bash
CUDA_VISIBLE_DEVICES=0 PYTHONPATH=src /isaac-sim/python.sh tools/xxx.py
```

`tools/run_remote.sh` 已内置（`IT_GPU`，默认 0）。顺带好处：8 张卡可以
同时跑 8 个互不干扰的实验，`IT_GPU=3 ./tools/run_remote.sh ...`。

**实测对照（13 次运行，单变量）**：

| 条件 | 传感器 | track_pose | 板数 | 结果 |
|---|---|---|---|---|
| 8 张全可见 | 有 / 无 | 开 / 关 | 1 / 2 | **全部崩** |
| `CUDA_VISIBLE_DEVICES=0` | 有 | 开 | 2 | 通过 |
| `=1` / `=2` / `=4` | 有/无 | 开/关 | 1/2 | 通过 |

**同一张物理 GPU0，不 pin 就崩、pin 上就过**——所以不是坏卡。

**未解释的残留**：`tools/s2_scripted.py` 在 8 张卡全可见时**不崩**，
S2 全程就是这么跑的。所以「多卡可见」是必要条件不是充分条件，
还有一个与 `DirectRLEnv` 相关的因素没定位。**但 pin 卡对两者都有效，
不再往下追**。若将来又冒出同类崩溃，先确认这条。

**代价与教训**：

这个坑烧掉了一整轮工作。另一个 agent 在它上面连试十几个变体、
改废了 `s3_source_drawer.py`，全程在改**本来就没错的代码**。

1. **崩溃不一定在代码里。** 换一台机器/换张卡/换个启动参数能过，
   就说明不是代码。这个对照应该**第一个**做，不是最后一个。
2. **`torch.cuda.synchronize()` 抓不到 PhysX 内部的 CUDA 错误。**
   分阶段打 OK 会给出**假的**定位——前 8 个 stage 全 OK，
   实际问题在别处。P-27 说「别猜，去测」，但测的方法本身也得先验证。
3. `CUDA_LAUNCH_BLOCKING=1` 在这里既没帮上忙也没添乱，与崩溃无关。

## P-30 · 逐点接触数据的 env 归属是错的，而且会整段丢失 ⭐⭐

**日期**：2026-08-29（S3 采集）

**现象**：三个症状，一开始看着毫不相干。

1. env 3 记到的接触点，转进物体系后 y 偏了 **−2223 mm**——恰好一个
   `env_spacing`。env 0 完全正常。
2. 某些 episode 抽屉明明被拉开了 **97 mm**，接触点却**一个都没有**。
   板压进横杆 0.5 mm（逐帧位姿可查），力就是不报。
3. 归类表里凭空出现 58% 的 `other` 部位。

- **下标不是 env 下标**。实测：只有 env 2 有接触时，`counts` 报
  `[0, 0, 0, 2]`、`start_idx` 报 `[0, 0, 0, 0]`——数量和位置都对，
  但**记在了 env 3 名下**。于是 env 3 拿到 env 2 的接触点。
- **总数会漏报**。按前缀和圈出的"新鲜槽位"覆盖不到全部真实接触点，
  落在覆盖范围外的点被整段忽略——症状 2 就是这么来的。

**为什么静态自检发现不了**：所有 env 同时有接触时，下标恰好是恒等的。
我先后写了两个静态对拍脚本（单板 / 双板 + 双传感器），**全部通过**。
只有在"接触逐个 env 先后建立"的真实采集里才会错开。

**解法**（`it.contact_utils.extract_contact_points_padded`）：

```text
counts/start_idx 只用来……什么都不用。
1) 扫全 buffer，取 |法向力| > 阈值的槽位
2) env 归属按"这个点离哪个 env 的传感器本体最近"判
3) 离所有本体都超过 own_radius 的点丢弃并计数（foreign）
```

修复前后（同一批 40 个 episode，同一 seed）：

| | 保留的接触点 | 成功率 | 接触落在 bar_back |
|---|---:|---:|---:|
| 前缀和切片 | 5730 | 52.5% | 52% |
| 扫全 buffer + 按位置归属 | **13786** | **77.5%** | **68%** |

**这条推翻了 P-18 的做法。** `extract_contact_points`（逐 env 循环版）
用的正是前缀和切片，它的数值本身没错，但 env 归属只在"所有 env 同时接触"
时才对。该函数因为是 S1/S2 的既有依赖而保留，docstring 里已加警告。

⚠️ **`decisions.md` D-34（钩杆接触部位分布）是用旧方法算的。** 当时 16 个 env
几乎同时接触，下标大概率是恒等的，但**没有验证过**。引用那组数字前应该重算。

**教训**：静态自检通过不等于对。这个坑的三个症状里，只有第 1 个像 bug，
第 2 个（接触整段消失）看起来像"物理没接触上"，第 3 个像"分类器阈值不对"——
我为后两个各写了一轮错误的修复。**把三个症状放在一起看，才看出是同一个根因。**

## P-31 · 一个控制步只在末尾采一次接触，会漏掉大部分接触

**日期**：2026-08-29（S3 采集）

**现象**：板与横杆的间隙逐帧稳定在 −0.5 mm（实实在在压着），抽屉被匀速拉开，
但按控制步采样的接触**有一半帧是空的**，`substep_contact_fraction` 只有 0.13。

**原因**：PhysX 只在**部分物理子步**里报告某个接触对。控制频率 50 Hz、
物理 300 Hz，一个控制步有 6 个子步；只读最后一个子步，就只能看到大约
1/6 的报告。接触是连续的，**报告不是**。

**解法**：每个物理子步都取一次，保留**法向力最大**的那一子步作为该帧的代表。
不是取最后一个，也不是求平均——平均会把"这一帧接触多大"稀释成"报告了几次"。

记录频率仍是 `plan/03` §5 规定的 50 Hz，改的只是"这一帧拿哪个子步代表"。

## P-33 · 力控轴的速度阻尼是相对世界的，物体一动就把接触力扣光

**日期**：2026-08-29（S3 采集）

**现象**：两种表现，看着完全无关：

- 指令力小的家族（每块板 2~3 N）**跟不上抽屉**，接触断断续续；
- 反向推的那块板（拇指，指令 −X 而抽屉往 +X 跑）**一接触就分离**，
  之后只剩阻尼、以 0.27 m/s 一路飘进柜体撞面板，把平均接触力顶到 30 N。

**原因**：`FloatingPD` 力控轴的输出是 `ff_force − kd_force·m·v_world`。
阻尼是**相对世界**的，而板必须跟着被操作物体走。抽屉以 0.2 m/s 打开时，
`kd_force=35`（→17.5 N·s/m）白扣 **2.3 N**，比某些家族的指令力还大。

**解法**：把 `kd_force·m·v_object` 前馈回去，等价于"阻尼相对被操作物体"：

```python
ff[:, 0] = -side * force_mag * engage + pd.kd_force * pd.mass * drawer_v
```

于是稳态接触力精确等于指令力，与物体开多快无关。
同一条思路对任何"跟着运动物体施力"的场景都适用，S4 之后的执行器同样要注意。

**顺带**：位置控制跟运动目标也有同一类问题——稳态滞后 `e = kd·v/kp`，
抽屉 0.2 m/s 时是 7.3 mm，乘 1500 N/m 的位置刚度就是 11 N 的"刹车力"。
所以不要用位置 PD 去跟一个在动的接触面，除非把滞后前馈补掉。

## P-34 · 薄板的姿态 PD 在 150 Hz 下数值不稳定，无接触时也偏 20°

**日期**：2026-08-29（S3 采集）

**现象**：采集板在**自由飞行、完全没有接触**的 approach 阶段，
姿态误差就稳定在 19~21°，峰值 74°。

**原因**：显式积分的姿态 PD 稳定条件是 `ω·dt < 2`，`ω = sqrt(kp_rot·m/I)`。
板 35×25×3 mm、0.05 kg，绕长边的 `I = m(b²+c²)/12 ≈ 2.6e-6 kg·m²`——
比钩杆小**两个量级**。本仓库其他地方的默认值 `kp_rot=50` 在 150 Hz 下给出
`ω·dt = 5.4`，直接发散成一个 20° 幅度的极限环。

**解法**（两条一起用）：

1. 采集用的物理步长 150 Hz → **300 Hz**（记录仍 50 Hz，decimation 6）。
   dt 减半，允许的刚度变成 4 倍。
2. 板质量 0.05 → **0.5 kg**。惯量正比于质量，这是不改尺寸的唯一办法。
   物理上也说得通——采集面背后本来就该有一只手或一段器械。

之后 `kp_rot=6`（`ω·dt = 1.2`），实测姿态误差 5.5°，峰值 12°。

**教训**：增益不能跨执行器照搬。**先算 `ω·dt`，再决定用不用。**

## P-35 · 用"离哪个面近"判接触落在薄板哪一面，一半会判错

**日期**：2026-08-29（S3 采集）

**现象**：验收表里凭空出现 **36% 的"拿边角蹭"**（`edge`），
而录像里板明明是拿正面压着横杆。

**原因**：板只有 3 mm 厚（半厚 1.5 mm），而 PhysX 报的接触点在两个表面之间
浮动——实测一次正常的**工作面**接触，点的局部 z 在 **0.3~1.7 mm** 之间摆。
用"离哪个面近"判，阈值放在哪儿都会把一半正常接触判成侧边。

**解法**：**按接触法向判，不按位置判**。实测 100% 的面接触满足
`|n_z| > 0.7`，且法向在板局部系里恒指向工作面朝外的方向（+Z）；
真正的棱边接触，法向躺在板平面内，`|n_z|` 明显小于 1。

改完 `edge` 从 36% 掉到 0%，`work_face` 100%。

**教训**：分类器出来的异常，先确认是**物理异常**还是**判据异常**。
这一条差点让我去"修"一个根本不存在的物理问题。
